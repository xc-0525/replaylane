# replaylane

**一个可观测、可恢复的任务执行管线。** 以「动画素材处理」为例：一条 8 步的管线，
有 GPU 重活、有非确定性步骤、有分钟级的单步耗时。单个步骤失败、进程被 kill -9、
整条任务跑一小时——这三种情况下系统都能自己接着跑，并且让上游随时看清楚"现在到哪了"。

零第三方依赖：Python 标准库 + SQLite。**没有 Redis、没有 broker、没有 Web 框架。**

```bash
python -m replaylane.cli serve --port 8000     # 打开 http://localhost:8000
```

```
任务
  QUEUED 排队 → RUNNING 执行中 → SUCCEEDED 成功 / FAILED 失败 / CANCELLED 已取消

步骤
  BLOCKED 阻塞 → READY 就绪 → CACHED 命中缓存（不执行）
                            ↘ QUEUED 排队 → RUNNING 执行中 → SUCCEEDED 成功
                            ↘ RETRY_WAIT 退避等待 → QUEUED
                            ↘ ATTENTION 待人处理 →（人工）→ QUEUED / FAILED
                            ↘ 租约过期 → QUEUED（回收，不是异常分支）
```

> 全部英文术语的中文对照见 [`docs/01` 附录 B](docs/01-架构与边界设计.md#附录-b术语)：
> 状态、调度与恢复、缓存与产物、管线步骤四组。

## 0. 三十秒跑起来

```bash
python -m replaylane.cli serve --port 8000      # 服务 + 2 个 worker 子进程
python -m replaylane.cli demo                   # 或者：命令行跑一个完整任务
python -m unittest discover -s tests -t .       # 7 个测试文件 / 40 个用例
python -m replaylane.cli verify                 # 用事件重放校验投影是否一致
```

要求 Python ≥ 3.10（用到 SQLite 3.35+ 的 `UPDATE … RETURNING`，启动时会断言）。
看板上可以直接注入四类故障：可重试失败、OOM 降级、`kill -9`、人工介入。

**想看故障注入**——每个命令换一个 `--source`，否则会命中上一次的缓存、0 秒跑完：

```bash
# 同一道工序连续失败两次再成功：重试 + 指数退避
python -m replaylane.cli demo --source a1.mp4 --fault matting:transient:2

# 显存不足：不是重试，是换更省显存的跑法（variant 变 bs_half）
python -m replaylane.cli demo --source a2.mp4 --fault matting:oom:1

# 跑到 45% 时把进程 kill -9：注意日志里"第 1 次"那行根本不存在
python -m replaylane.cli demo --source a3.mp4 --fault restyle:kill:0.45

# 对照组：restyle 的重试白名单是空的，同样的故障直接失败、下游全取消
python -m replaylane.cli demo --source a4.mp4 --fault restyle:transient:1

# 人工闸门：停在 ATTENTION，去大屏点"通过"才继续（命令行会一直等到 --timeout）
python -m replaylane.cli demo --source a5.mp4 --human-gate --name "片头重绘"
```

`--fault` 格式：`步骤:故障类别[:次数]`，kill 写成 `步骤:kill:比例[:第几次]`，可重复多次。
**命令行不需要写 JSON**——PowerShell 会吞掉 JSON 里的双引号，所以专门留了这套参数
（仍支持 `--params '<json>'` 与 `--params-file x.json`）。

## 1. 实现方式与时间规划

**分七层，一条写路径。** `schema.sql` 全部 `DDL`（建表语句）一个文件；`db.py` 只提供三件事
（写事务、`CAS`（带条件的更新）、事件追加）；`model.py` 是状态转移表与失败裁决的唯一真源；
`scheduler.py`（调度器）是唯一决定"下一步干什么"的地方；`worker.py`（执行进程）是唯一
执行步骤的地方；`sweeper.py`（清扫器）只做回收；`server.py` 只有路由。

**关键取舍：不做应用内单写线程，靠 SQLite 文件锁做单写者。** 因为 worker / scheduler /
sweeper 是三个独立进程，应用内线程池管不到跨进程写入。少一个组件，多进程天然安全；
代价是写冲突靠 `busy_timeout`（锁等待超时）重试，高并发下 `p99`（慢请求分位值）会抖。

时间规划按"先让失败可见，再让成功好看"排：schema 与状态机 4h → 调度与执行 5h →
worker/sweeper 4h → 看板 6h → 故障注入与断言 4h → 文档与录屏 4h，另留 2h 缓冲。
实际代码 **3382 行**（另 736 行测试），与设计的 3070 行预算基本吻合。

> 详细推导见 [`docs/01-架构与边界设计.md`](docs/01-架构与边界设计.md)（第 1 章）。

## 2. 长任务、状态管理与失败恢复

**核心是一条断言**：任何写入都必须同时匹配 `(lease_id 租约号, fencing_token 令牌号)`。
租约说明"你现在有执行权"，令牌说明"你是第几任"。被 kill 的 worker（执行进程）复活后
拿着旧令牌提交，`rowcount`（受影响行数）为 0，它自己就知道该退出了。

- **恢复不是异常分支。** `sweeper`（清扫器）发现 `last_beat`（最后一次心跳）超时 →
  关租约 → 把步骤放回 `QUEUED`（排队）→ 走正常调度。全代码没有一处 `if crashed then recover`。
- **执行权与心跳拆表。** 心跳是 4 次/秒的热行更新，对"重启后的决策"毫无价值，
  单独放 `lease`（租约表），只更新一列。
- **三层恢复**：任务级（重新提交）、步骤级（重试/降级）、步骤内（`checkpoint` 检查点分片）。
- **11 类失败**各有明确动作：可重试 / 换 `variant`（降级档位）/ 转人工 / 直接失败 / 取消。
  裁决规则写死在 `model.decide()`：**分类表是唯一真源**，步骤上的 `retry`（重试）预设只
  声明"类别白名单 + 退避曲线 + 预算上限"，冲突取严。
- **OOM（显存不足）不是重试，是降级**：`base → bs_half → tiled → small_model → 人工`。
  降级参数记在 `attempt.variant`，**不进 step_key**——否则同一逻辑步骤会分裂成多条
  缓存线，命中率崩塌。
- **人工环节是闸门，不是一次计算。** 走到 `idem="human"` 的步骤时 worker 不执行，而是挂起
  在 `ATTENTION`（`attempt` 记 `SUSPENDED`，**不是失败**，否则失败率统计会被正常审核污染），
  等人点「通过」；那一下会补一条 `human:<名字>` 的成功记录。

> 详见第 4 章（11 类失败矩阵）、第 8 章（秒级 → 小时级的 14 项参数变化与 6 个质变）。

## 3. 步骤与依赖怎么定义

代码即配置。`pipeline.py` 里 8 个步骤就是 8 个 `frozen dataclass`（不可变数据类）：

| 步骤 | 中文 | 干什么 | 成本权重 | 显存 | 复用策略 |
|---|---|---|---|---|---|
| `probe` | 探测 | 读视频元信息 | 2 | — | 确定性 |
| `shot_split` | 分镜切分 | 按镜头切换点切片 | 50 | — | 确定性 |
| `frames` | 抽帧 | 解码成图像序列 | 90 | 2 GB | 确定性 |
| `matting` | 抠像 | 主体与背景分离 | 600 | 12 GB | 确定性 |
| `restyle` | 风格重绘 | 逐镜头改画风，**占 60% 成本** | 1800 | 20 GB 独占 | **非确定性**（seed 进 key） |
| `temporal` | 时序校正 | 消除跨帧闪烁与接缝 | 420 | 8 GB | 确定性 |
| `encode` | 转码 | 编回一个视频文件 | 60 | 1 GB | 确定性 |
| `qc_review` | 人工质检 | 人看一眼放行 | 0 | — | **不缓存，且要停下等人** |

```python
Step("restyle",            # 步骤名
     ("matting",),         # 依赖：等「抠像」完成
     cost=1800,            # 成本权重：进度按它加权，不按步数
     gpu_mb=20480,         # 申请 20GB 显存
     gpu_mode="exclusive", # 独占整卡
     retry="never",        # 重试白名单为空：429 也不重试
     idem="nondet",        # 非确定性：同一输入两次结果不同
     checkpoint="per_shot", shards=12)   # 每镜头一个检查点，共 12 片
```

依赖用 `deps` 元组表达，声明顺序即拓扑序（有 `check_dag()` 校验）。
**下游的缓存键依赖上游产物的摘要，所以 key 必须等上游跑完才算得出来**——
这不是性能优化，是内容寻址的必然结果。唯一的例外是 `probe`（探测，无依赖）。
所以"提交时预生成整棵 DAG（有向无环图，即步骤依赖网）的 key"在逻辑上不可能。

`step_key`（步骤指纹）= `sha256(pipeline, version, step, 语义参数, 依赖产物摘要, seed?)`。
`seed` 只在非确定性步骤里进 key，默认由参数哈希派生：**相同参数 → 相同 key → 全量
复用；换 seed → 从 `restyle` 开始重新生成**。

两个例外，都是刻意的：

- **人工环节永不命中缓存。** 人看过并通过是针对"这一次交付"的判断，不是输入的属性，
  复用等于让新交付免检。所以完全相同的任务是"7 步复用 + 1 步人工重走"：零算力，但不等于零人工。
- **名字、故障注入、`auto_approve` 都不进 key。** 它们描述"怎么跑"，不描述"跑什么"。
  否则给任务改个名字都会导致 8 步全重跑。

> 详见第 3 章（DSL、字段、四类复用策略、哪些步骤适合做独立可恢复任务的 5 条判据）。

## 4. 持久化了哪些状态，为什么

12 张表，按"重启后还用不用得上"分三类：

| 必存（重建不了） | 中文 | 为什么 |
| --- | --- | --- |
| `task` / `step_run` | 任务 / 步骤实例 | 逻辑进度。丢了就不知道做到哪一步 |
| `attempt` | 一次尝试 | 执行历史。append-only（只追加），同一 `step_run` 的 5 次尝试各有各的死法 |
| `lease` | 租约 | 崩溃检测的唯一依据。**没有它就只能靠猜** |
| `checkpoint` | 检查点 | 步骤内断点。分片绑定 `(step_key, seed, attempt_no)`，防止把两个 seed 的产物拼在一起 |
| `artifact` / `artifact_ref` / `step_cache` | 产物 / 产物引用 / 步骤缓存索引 | 产物与两种引用（任务引用 + 缓存索引） |
| `event` | 事件 | 真源（source of truth）。投影（当前状态表）可从它重建，它永不从投影重建 |
| `gpu_lease` | 显存租约 | 显存账本。进程重启后据此知道谁占着卡 |

**不存**：内存队列（队列表就是 `status='QUEUED'`（排队）的索引）、进度百分比（可算）、
重试计数（`attempt` 表里数）、worker 存活状态（租约即真相）、临时中间态文件。

有一个容易忽略的：**`artifact`（产物）必须有 `last_access_at`（最后访问时间）**。
`GC`（垃圾回收）的判据是 `无 artifact_ref 引用 AND 无 step_cache 引用 AND 老化超时`——
只按前者判会删掉仍在缓存索引里的产物，下一个任务命中缓存时拿到一个不存在的路径，而且不报错。

> 详见第 5 章（必存 10 项 / 不存 8 项 / 事件与投影的边界）。

## 5. 用了什么 AI 工具、大概多少 token

主力：对话式编码助手（方案推演、代码生成、文档重写）；次要：编辑器内联补全。

| 阶段 | 占比（估） | 说明 |
| --- | --- | --- |
| 设计与文档迭代 | ~35% | 每改一章都要把全文（表格、SQL）重新带进上下文 |
| 后端代码 | ~25% | 模块小、上下文局部，单次生成成功率高 |
| 前端看板与甘特 | ~15% | CSS 与图表试错，来回多但每次短 |
| 调试与返工 | ~25% | 6 个真 bug 全出在这里，见 §7 |

**最烧的两件事**：①「通读全文再改第 N 章」——每次都是数万 token 的输入，改完还要连带改
相邻章节；②反复重写同一个小节，让表达不像教科书。**token 花在"表达"上比花在"逻辑"上多。**

总量级：设计阶段 30–60 万，实现与调试 100–150 万，全流程约 150–220 万（含缓存命中）。
口径 = 工具用量页的"输入 + 输出 tokens"，包含缓存命中部分。

## 6. 个人时间花最多的部分（不含 LLM 直接产出）

个人净投入约 **14 小时**（另有约 20 小时由 AI 产出与联调，合计与 §1 的 34 小时预算对齐）。

| 事项 | 小时 | 说明 |
| --- | --- | --- |
| 状态机与边界推演 | 4 | "僵尸 worker 复活""断电后账本不一致""全缓存任务卡住"这类反例，AI 不会替你想 |
| **接口与边界测试** | **5** | **最花时间**。见下面这段 |
| 看板可视化验证 | 3 | 功能对但界面骗人，反复改提示与配色 |
| 文档与校对 | 2 | README、设计稿、术语表 |

**最花时间的是测试，不是写代码。** 而且真正有价值的 bug 几乎都不是"代码写错了"，是
**"功能对了但看不见"**：全部命中缓存时界面像卡死、崩溃后的空窗被画成执行中、降级看不出
换过跑法。这些都是我手点出来的——AI 只会按主流程跑一遍，边界情况和不合法的输入它不会主动试。

## 7. 失败案例：做错的地方

**① 人工审核被缓存直接跳过（设计错）**

最初把 `qc_review` 当成普通步骤，于是"第二次提交同样参数"时它命中缓存、直接通过——
等于让新交付免检。人工通过是针对**这一次交付**的判断，不是输入的属性。
改法：人工步骤永不查缓存、也不写缓存索引；并且真的停下来等人在看板上点「通过」。

**② 用"名字"参与缓存键（会白烧钱）**

给任务加命名时，第一反应是把它塞进 `params` 就完事——但 `params` 会进 `step_key`，
结果是"改个名字 → 8 步全部重跑"。名字只是给人看的标签，必须排除在指纹之外。
现在 `name` 和 `faults`、`auto_approve` 一样，都在 `NON_SEMANTIC_KEYS` 里。

**③ 重试按钮点了没反应（路由下标错位）**

`/api/tasks/{id}/steps/{name}/retry` 拆成 6 段，却写成 `parts[4] == "retry"`——而 `parts[4]`
其实是步骤名，条件永远不成立，请求落到 404。前端口径又把 404 说成"当前状态不允许"，
于是看起来像业务拦截。教训：**接口层必须有测试**，现在补了 12 个路由用例。

**④ 重试后步骤永久卡在队列**

重试时把 `gpu_ready` 清成 0（对的，失败时显存已经还了），但调度器只会给**需要显存**的
步骤重新批显存——不需要 GPU 的人工质检就永远等不到那个 1，谁也不敢领。
教训：清理逻辑的副作用范围要显式约束，"不需要资源"也是一种需要显式处理的状态。

**⑤ 缓存的返回值两条路径口径不一致**

真跑成功时写的是产物 sha，命中缓存时写的是产物**集合**摘要。上游两条路径产生的 digest
不同 → 下游 key 永远对不上 → 缓存只有第一层能命中。
教训：同一个语义值必须由**同一个函数**产生，否则它只是"看起来一样"。

**⑥ 事件记全了，但图只画了一部分**

甘特最初只认 6 种事件，于是"崩溃后的 15 秒空窗"被画成执行中、"降级换跑法"被画成一条
连续的蓝条。数据没错，是可视化在骗人。改法：给 `lease.expired` 补 `silent_ms`，
把空窗单独切成 `dead` 段；`step.degraded` 也补了颜色与标记。

> 设计阶段还有 6 个自我修正（用状态字段当锁、心跳写主表、按步数算进度、预生成 DAG key…），
> 见 [`docs/01` 第 10.3 节](docs/01-架构与边界设计.md)；实现阶段更完整的版本在第 10.4 节。

**做不了 / 主动不做**：跨服务 exactly-once（物理上不可能，只能 outbox + 对账）；
可恢复 ≠ 可复现（非确定性步骤重跑必然不同，只能靠"永不重跑、只复用"绕开）；
多机、多租户、HA（明确列为不做，理由在 §9.1）。
