## 一、三个决策

### D1 甘特坐标系：顺序用 `seq`，宽度用 `mono_ms`

01 的 6.5 与 10.3 案例 6 曾经互相否证：一处说 x 轴用 `seq`，另一处说条宽是执行时长。
用 `seq` 做单位的话，退避 64 秒期间零事件，灰条宽度恒为 0——而灰条恰恰是这张图上最该
被看见的东西。

**决定**：`event` 表同时存两列。

| 列 | 类型 | 用途 |
|---|---|---|
| `seq` | INTEGER 自增 | 事件排序、SSE 游标、断线重连。回滚会烧号，允许空洞 |
| `ts` | TEXT ISO8601 | 人类可读、日志、算"多久以前" |
| `mono_ms` | INTEGER | **只用于算差值**：甘特条宽、执行时长 |

**代价**：`time.monotonic()` 跨重启归零，所以跨重启的历史事件不能用它算宽度。
演示只覆盖单次开机，接受这个边界（已写进 01 的 9.3）。

### D2 非确定性步骤的 seed：把 seed 变成输入的一部分

`restyle` 的三种说法在 01 里是互斥的："绝不重跑" / "无产物才换 seed 重跑" / "读 checkpoint
从断点继续"。真正的冲突在于：换 seed 就等于换输入，而换输入就是换 `step_key`——
那它根本不是"同一步骤的重试"，而是"另一个任务的首次执行"。

**决定**：

1. `seed` 属于**任务级语义输入**，默认由语义参数的哈希派生：
   `seed = int(sha256(canonical_params)[:8], 16)`。
   → 相同参数 → 相同 seed → 全量命中缓存（"再提交一次，0 秒完成"是真的）。
   → 想换一批画面 → 显式给 `seed` → 换 key → 重新生成。
2. **重试永远不换 seed**（同任务同 seed，结构上保证）。
3. `checkpoint` 分片绑定 `(step_key, seed, attempt_no)`，读取时三列全匹配才采纳。
   → 从根上杜绝"前 6 个镜头 seed A、后 6 个镜头 seed B"的混合产物。
4. 降级参数（`variant`）**不进 key**，只记在 `attempt` 上。

### D3 重试裁决：分类表是唯一真源，`retry` 预设只是白名单

01 里 `restyle retry="never"` 与 4.2「429 指数退避 8 次」直接冲突，全篇没有裁决规则。

**决定**（实现于 `model.decide()`）：

- **4.2 的分类表是"类别 → 动作"的唯一真源。**
- 步骤上的 `retry` 预设只声明三件事：允许重试的**类别白名单**、退避曲线、同一 variant
  的失败次数上限。冲突取严（白名单为空 = 不重试，`restyle` 的 429 也不重试）。
- **`retry` 与 `degrade` 是两件事，各有各的预算**：
  - `retry` = 同参数再跑一次，受 `max_same_variant` 约束；
  - `degrade` = 换 variant 再跑，受 OOM 阶梯（4 级）约束。
  - 所以 `restyle` 虽然是 `never`，OOM 时仍会降级——**"换个跑法"不是"再试一次"**。

### D4 人工步骤不参与缓存

`qc_review` 的 `idem` 是 `human`。它**永远不查缓存、也不写缓存索引**。

理由：「人看过并通过」是针对**某一次交付**的判断，不是「这个输入」的属性。同一份成片
第二次提交时，时限、版权、客户可能都变了，复用上一次的通过等于让新交付免检。

实现上就两处：`scheduler.resolve()` 对 `idem == "human"` 跳过 `_cache_hit`；
`worker._commit()` 对 `idem == "human"` 不写 `step_cache`（否则会留一条永远不用的
索引行，还会让 GC 误判产物有人引用）。

**副作用**：一个「参数完全相同」的任务不再可能 100% `CACHED`——7 步复用，人工审核那步
每次都要重走。这是对的：零算力不等于零人工。

### D5 人工环节是一个"闸门"，不是一次"计算"

走到 `idem="human"` 的步骤时，worker 不执行，而是**挂起**：

- `step_run` → `ATTENTION`，`blocked_reason='awaiting_human'`
- `attempt` → **`SUSPENDED`**（不是 `FAILED`——否则每一次正常审核都会污染失败率）
- 关租约、还显存，执行权干净交出
- 任务停在 `RUNNING`（有一个非终态步骤），进度封顶 99%

人点「通过」调 `scheduler.approve()`：步骤直接记 `SUCCEEDED`，并补一条
`worker_id='human:<名字>'` 的 `SUCCEEDED` attempt——**人工环节的执行者就是人**，
所以不再让机器跑一遍。事件写两条：`step.approved`（谁批的）+ `step.succeeded`
（变成了什么），缺后者事件重放就重建不出终态。

`params.auto_approve=true` 是给自动化测试和一键演示用的旁路，默认关闭；
`demo` 子命令默认开启，加 `--human-gate` 可以打开闸门。

## 二、与 01 的其它偏离

| # | 01 里写的 | 实现里做的 | 为什么 |
|---|---|---|---|
| 1 | 应用内**单写线程** + 队列 | 依赖 SQLite 文件锁（`BEGIN IMMEDIATE` + `busy_timeout`） | worker / scheduler / sweeper 是三个独立进程，应用内线程池管不到跨进程写入。少一个组件，多进程天然安全；代价是写冲突重试，p99 会抖（01 §9.3 第 7 条） |
| 2 | 有独立的 `faults.py` | 没有这个文件，故障注入在 `params.faults` 里 | 少一个"只在演示时才走"的代码路径。注入点就是步骤执行本身 |
| 3 | 目录树里没有 `verify.py` / `cli.py` | 都有 | `verify` 是"事件是真源"唯一的检验手段；`cli` 让"一个进程能演全部角色"成立 |
| 4 | `attempt.ended_at` 对 `ABANDONED` 也有值 | 故意留 NULL，另存 `observed_at` | kill -9 之后确实不知道它几点死的。给它一个精确的 `duration_ms` 是自欺欺人，而且这个数会被当成真实执行时长做归因 |
| 5 | `gpu_lease` 无 `worker_id` / `fencing_token` | 两列都加 | 孤儿清理要按 token 判，不能按 worker 判——断电时 worker 本身就不存在了 |
| 6 | `WAITING_EXTERNAL` 状态 | 不存在，用 `RETRY_WAIT + blocked_reason` | 不想为一个提示语新增状态，否则三张状态机都要改 |
| 7 | 事件每月归档，SSE 用 `Last-Event-ID` 续 | 未做归档 | 演示规模下 event 表不会超过内存。**归档一旦启用，必须补"游标早于库内最小 seq 时返回快照"的兜底**，否则客户端永远补不齐 |
| 8 | 卡住检测按 `2 × checkpoint 间隔` | 按 `step_run.stall_after_ms`（默认 5 分钟） | 每个步骤的卡住阈值不同，从 step_spec 读更合理；实现里给的是保守默认值 |

## 三、字段清单

01 §2.1 只写了"八个实体各自的一句话职责"，正文 SQL 里却引用了十来个从未定义的列。
实现时补了这张表（`schema.sql` 是最终真源，这里是索引）：

| 表 | 列 | 类型 | 含义 |
|---|---|---|---|
| `step_run` | `gpu_ready` | INT 0/1 | 显存已批下来。领取 SQL 用它过滤，所以它在索引里 |
| | `ready_seq` | INT | 入队序号，同优先级下的稳定顺序（老化后用它兜底） |
| | `queued_at` / `requeued_at` | TEXT | 老化计算的基准（`eff_priority = priority - ⌊wait/300⌋`） |
| | `spec_cost` | INT | 冗余自 `step_spec.cost`，避免投影时 join |
| | `fencing_token` | INT | 单调递增，所有写入的 WHERE 条件 |
| | `attempt_no` | INT | 已发放的 attempt 数（只增，不复用） |
| | `variant` | TEXT | OOM 降级阶梯的当前位置（`base/bs_half/tiled/small_model`） |
| | `retry_at` | TEXT | `RETRY_WAIT` 的唤醒时刻 |
| | `last_progress_at` | TEXT | 卡住检测的比较基准 |
| | `stall_after_ms` | INT | 该步骤的卡住阈值 |
| | `blocked_reason` | TEXT | `external_unavailable` / `progress_stalled` / `upstream_failed` |
| | `output_digest` | TEXT | **产物集合摘要**（不是单个产物 sha），见 10.4 案例 ② |
| `attempt` | `started_mono_ms` / `ended_mono_ms` | INT | 执行时长，不受 NTP 影响 |
| | `observed_at` | TEXT | `ABANDONED` 时 sweeper 的判定时刻 |
| | `variant` | TEXT | 这次尝试用的降级档位 |
| `artifact` | `last_access_at` | TEXT | GC 老化依据；命中缓存时刷新 |
| `checkpoint` | `(step_run_id, shard)` | PK | 分片号是主键的一部分 |
| | `(step_key, seed, attempt_no)` | — | 采纳条件，三列必须与当前一致 |
| `gpu_lease` | `worker_id` / `fencing_token` | — | 孤儿清理的判据 |

**`output_digest` 的口径写死在这里**：`sha256("".join(sorted(artifact_shas)))`。
真跑成功与命中缓存两条路径必须走同一个函数（`steps.aggregate_digest`），
否则下游 key 会对不上——这是实现期最贵的一个 bug，详见 01 §10.4。
